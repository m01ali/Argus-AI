# Metasploitable - unauthenticated root shell on port 1524 (ingreslock)

### Summary
During a security assessment of the host, a critical vulnerability was identified on TCP port 1524 (historically associated with the `ingreslock` service). This port exposes an interactive, unauthenticated command shell running with administrative (root) privileges. Any remote attacker who can establish a TCP connection to this port is instantly granted complete, unrestricted command-line control over the operating system without providing a username, password, or any form of cryptographic credential.

* **Severity:** Critical
* **Justification:** This vulnerability represents a complete compromise of the system's confidentiality, integrity, and availability (CIA triad). An attacker can execute arbitrary commands, read or modify sensitive data, install malware, or pivot into adjacent networks. Because it requires zero authentication and no user interaction, the complexity of exploitation is trivial, leading to a CVSS v3 score of 10.0 (Critical).

---

**Key findings from the raw connection:**
1. **Instant Shell Execution:** Upon connection, the command `id` was run immediately, returning `uid=0(root) gid=0(root) groups=0(root)`. This verifies that the shell process inherits the highest privilege level on the system without validating identity.
2. **Identity Verification:** The command `whoami` confirmed the active user context is `root`.
3. **Target System Identification:** Running `uname -a` and `hostname` returned the kernel release (`6.6.87.1-microsoft-standard-WSL2 #1 SMP PREEMPT_DYNAMIC`) and hostname (`214dcb0131f9`), proving live access and interactive execution capability on the host.
4. **Data Exfiltration:** Running `head -n 20 /etc/passwd` successfully extracted system user definitions, proving unrestricted read access to critical configuration files.

### Root Cause
This vulnerability is caused by a **bind-shell backdoor** running on the host. A bind-shell backdoor is a configuration where a shell command interpreter (such as `/bin/bash` or `/bin/sh`) is directly bound to a listening network socket, waiting for incoming TCP connections to attach to its standard input, output, and error streams. 

This backdoor is typically configured in one of two ways:
1. **Super-server Configuration (inetd/xinetd):** A line in `/etc/inetd.conf` or a configuration file in `/etc/xinetd.d/` mapping the `ingreslock` service (TCP port 1524) to directly launch a root shell, such as:
   ```text
   ingreslock stream tcp nowait root /bin/bash
   ```
2. **Prior System Compromise:** An attacker previously obtained unauthorized access to the host and placed a standalone persistence script or listener (e.g., using `netcat`, `socat`, or custom binaries) to maintain persistent access.

This is not a legitimate service, and there is no secure use case for exposing a shell directly over unauthenticated TCP.

### Remediation

#### Immediate Steps
1. **Network Isolation:** Immediately block all inbound TCP traffic to port 1524 using network-level or host-level firewalls.
2. **Identify and Terminate the Process:** Locate the active listening process on port 1524 and kill it. Run the following command to identify the Process ID (PID):
   ```bash
   ss -ltnp | grep :1524
   # Or using netstat:
   netstat -ltnp | grep :1524
   ```
   Once the PID is identified, terminate the process:
   ```bash
   kill -9 <PID>
   ```
3. **Disable Persistent Configuration:**
   - Inspect `/etc/inetd.conf` and all files inside `/etc/xinetd.d/`.
   - Remove or comment out any entries referencing port `1524`, `ingreslock`, or launching `/bin/bash` / `/bin/sh`.
   - Restart the super-server daemon to apply changes:
     ```bash
     systemctl restart inetd   # or xinetd, depending on the system init manager
     ```
4. **Assume Full Compromise and Rebuild:** Because a pre-existing root backdoor has been found, the operating system's integrity cannot be guaranteed. The attacker may have modified kernel space, installed rootkits, or compromised system credentials. The host must be treated as completely untrusted. 
   - Decommission the current virtual machine or container.
   - Rebuild the host from known-good, trusted base images.
   - Do not reuse any local configuration files, binaries, or credentials without a thorough cryptographic and manual security audit.

#### Preventive Controls
1. **Host-Based Default-Deny Firewall:** Implement a local packet filter (e.g., `iptables`, `nftables`, or `ufw`) configured with a strict **default-deny inbound** policy. Only explicitly authorized administrative ports (such as SSH over an authenticated, restricted subnet) should be allowed.
2. **File Integrity Monitoring (FIM):** Deploy a file integrity monitoring tool (e.g., Samhain, AIDE, or Tripwire) to monitor critical system files and directories, such as `/etc/`, `/bin/`, `/usr/bin/`, and boot scripts. This ensures any unauthorized changes or newly introduced persistence binaries are flagged immediately.
3. **Egress Filtering:** Implement outbound network filtering to prevent the host from establishing arbitrary outbound connections. This restricts an attacker's ability to pull down malicious tools, establish reverse shells, or download rootkits.
